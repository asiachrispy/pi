# Pi 模块诊断与优化计划

## Summary

当前 monorepo 主要由 4 个包组成：`pi-ai`、`pi-agent-core`、`pi-coding-agent`、`pi-tui`。代码规模约 100k LOC，其中 `coding-agent` 约 49k、`ai` 约 31k，是主要复杂度来源。优化目标是降低大文件耦合、稳定 provider/session/TUI 边界、提升测试分层和发布可维护性。

注意：当前工作树有未提交修改 `packages/ai/src/image-models.generated.ts`，诊断计划默认不覆盖该文件，除非后续明确要求处理生成文件。

## Module Diagnosis

- `packages/ai`
  - 现状：provider adapter 密集，`models.generated.ts` 超大，`anthropic/openai-codex/openai-completions/amazon-bedrock` 文件偏大。
  - 风险：provider 兼容逻辑分散，模型元数据生成与人工修改边界容易混淆，e2e 测试和普通测试混杂。
  - 优化方向：抽出 provider shared compatibility 层；强化 generated 文件只读规则；按 provider 建立 focused contract tests。

- `packages/agent`
  - 现状：核心 agent loop、harness、session、compaction 边界较清晰，代码量最小。
  - 风险：`agent-harness.ts`、`agent-loop.ts`、`harness/types.ts` 承载过多协议和状态细节。
  - 优化方向：拆分 turn lifecycle、tool execution settlement、session persistence adapters；保留 public harness API 稳定。

- `packages/coding-agent`
  - 现状：最大模块，包含 CLI、interactive、RPC、SDK、extensions、settings、package manager、session manager。
  - 风险：`interactive-mode.ts` 约 5.7k 行、`agent-session.ts` 约 3.1k 行、`package-manager.ts` 约 2.6k 行，是主要维护风险。
  - 优化方向：按控制器拆分 interactive mode；把 session queue/compaction/tree navigation 分离；把 package manager parse/install/update/trust 逻辑拆层。

- `packages/tui`
  - 现状：TUI 基础库独立，editor、keys、tui renderer 是核心复杂点。
  - 风险：terminal key 协议、editor 状态、render diff 容易产生平台回归。
  - 优化方向：建立 key parsing fixtures；把 editor model 与 rendering/input adapter 分离；增加 render perf smoke。

## Key Optimization Work

- Architecture boundaries
  - 明确依赖方向：`ai -> none`，`agent -> ai`，`tui -> none`，`coding-agent -> ai/agent/tui`。
  - 增加轻量 boundary check，禁止底层包反向依赖 `coding-agent`。
  - 为 `coding-agent` 内部建立 `core/session`、`core/extensions`、`core/packages`、`modes/interactive` 的 owner map。

- Large file reduction
  - `interactive-mode.ts`：拆出 command dispatch、message rendering orchestration、overlay/editor state、session navigation handlers。
  - `agent-session.ts`：拆出 queue management、compaction workflow、tree navigation、runtime event bridge。
  - `package-manager.ts`：拆出 source parsing、install roots, npm/git installers, update planner, trust validation。
  - `ai/providers/*`：提取 shared request normalization、retry/error classification、tool schema conversion。

- Test strategy
  - 把 e2e/provider-auth tests 明确标记并隔离，默认 `./test.sh` 不触发真实 provider。
  - 对大模块拆分前先加 characterization tests，避免重构时改变行为。
  - 为 `interactive-mode` 和 `tui` 增加 terminal fixture snapshots，覆盖 key sequences、overlay focus、render width。
  - 为 `package-manager` 增加 table-driven tests，覆盖 npm/git/path/trust/offline/cache cases。

- Build and release hygiene
  - 继续保持 `npm run check` 作为代码变更门禁。
  - generated model files 只通过 scripts 更新。
  - lockfile/shrinkwrap 变更单独 review，提交时显式列路径。
  - 建议增加 `npm run check:boundaries` 和 `npm run check:large-files`，先 warning 后 enforce。

## Execution Phases

- Phase 1: Baseline
  - 记录 LOC、大文件、test runtime、check runtime、known flaky/e2e tests。
  - 输出模块依赖图和大文件拆分目标。
  - 不改业务逻辑。

- Phase 2: Safety Net
  - 给 `interactive-mode`、`agent-session`、`package-manager`、provider adapters 补 characterization tests。
  - 固化当前行为，优先覆盖 session branching、queue settlement、tool execution、provider conversion。

- Phase 3: Refactor
  - 每次只拆一个高风险文件，保持 public API 不变。
  - 每个拆分 PR 包含对应 focused tests 和 `npm run check`。
  - 不混入功能改动。

- Phase 4: Performance and DX
  - 增加 render/provider/session micro-bench 或 smoke 指标。
  - 优化 test 分类和命令文档。
  - 增加 CI 检查边界和大文件增长。

## Test Plan

- 每个重构单元运行对应 package focused tests。
- coding-agent 改动后运行 `npm run check`。
- 新增/修改测试文件时运行具体测试文件。
- 非 e2e 使用 `./test.sh` 或 package-specific vitest；不直接跑全量 vitest。
- 涉及 TUI 交互时使用 tmux smoke 或 terminal fixture tests。

## Assumptions

- 优化优先级：可维护性和回归风险控制高于快速拆文件。
- 默认不改变 public APIs、CLI 命令、session JSONL 格式、extension API。
- 默认不处理当前 dirty 的 `packages/ai/src/image-models.generated.ts`。
- 不引入新依赖；如确需依赖，单独做依赖安全 review。
